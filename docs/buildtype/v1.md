# TeamCity SLSA build type — `v1`

This document defines the provenance fields generated by the plugin. The stable `buildType` URI is:

```text
https://iaroslav-molochkov.github.io/teamcity-slsa-plugin/buildtype/v1
```

The plugin generates provenance from TeamCity server APIs and signs it on the server.
The output is an [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)
with a [SLSA v1.2 provenance predicate](https://slsa.dev/spec/v1.2/build-provenance):

- `_type`: `https://in-toto.io/Statement/v1`
- `predicateType`: `https://slsa.dev/provenance/v1`

The statement is signed in a DSSE envelope with payload type `application/vnd.in-toto+json`
and published in a Sigstore bundle as `provenance.sigstore.json`.

## Conventions

- All fields are serialized with empty/null values omitted. A field documented as *optional* is
  absent (not null, not empty, never a placeholder such as `"unknown"`) when it does not apply.
- Map/object keys are serialized in sorted order; this carries no semantic meaning.
- Timestamps are RFC 3339 / ISO-8601 UTC instants (e.g. `2026-06-23T10:05:00Z`).
- Digests are lowercase hex, keyed by algorithm (an in-toto `DigestSet`).

## Trust model

The parameter sections distinguish requester inputs from recorded build metadata:

- `externalParameters` — values the requester supplies through the build-trigger interface.
  Untrusted; a verifier must check them.
- `internalParameters` — build metadata recorded by the platform (`runDetails.builder.id`).
  Consumers rely on the trusted platform to report these values accurately.

Build metadata is read from TeamCity server APIs. Some values, such as the displayed build number,
can be set by build steps.

## Subjects

`subject[]` lists every **file artifact** the build published, as seen server-side in the default
artifact view (build-internal service artifacts, such as the hidden `.teamcity` directory, are
excluded). Each entry:

| Field            | Type   | Meaning                                              |
|------------------|--------|------------------------------------------------------|
| `name`           | string | Artifact path, relative to the build artifact root.  |
| `digest.sha256`  | string | SHA-256 of the artifact content, lowercase hex.      |

A build that publishes no file artifacts produces no attestation.

## `buildDefinition.externalParameters`

Requester-supplied inputs passed through the build-trigger interface. Untrusted; a verifier checks
them. The recorded fields are listed below.

| Field         | Type    | Req. | Meaning                                                                       |
|---------------|---------|------|-------------------------------------------------------------------------------|
| `buildTypeId` | string  | yes  | Build configuration external id (e.g. `MyProj_Build`).                        |
| `projectId`   | string  | yes  | External id of the project that owns the build configuration (stable scoping for policy). |
| `branch`      | string  | no   | Logical build branch the run was requested on (see below).                    |
| `personal`    | boolean | no   | Present and `true` only for *personal* builds — the requester supplied a private patch on top of the VCS revision (user-private, not shared). |
| `customBuildParameters` | object | no | Requester-supplied custom build parameters, when enabled (see below). Omitted by default. |

`branch` is the logical build branch. It is absent in configurations without a branch specification,
and is `"<default>"` only when a configuration with a branch specification runs its default branch.
The per-repository ref appears in `resolvedDependencies[].annotations.branch`. No derived
default-branch flag is emitted.

By default `externalParameters` is a curated subset: build parameters are excluded for secret safety.
The `slsa.includeCustomBuildParameters` feature option adds `customBuildParameters` (see below).

### `customBuildParameters`

Present only when the `slsa.includeCustomBuildParameters` feature option is enabled. Holds the build's
requester-supplied custom parameters (`BuildPromotion.getCustomParameters()`). Declared secrets are
dropped: parameters typed `password`, parameters whose key has the `secure:` prefix, and any reported
by a registered `PasswordsProvider`. Detection covers declared secrets only — a secret placed in a
plain parameter is not detected, so do not put secrets in plain parameters.

## `buildDefinition.internalParameters`

Build metadata recorded by the platform and read from server-side APIs. Consumers rely on the
trusted platform to report these values accurately.

| Field           | Type    | Req. | Meaning                                                  |
|-----------------|---------|------|----------------------------------------------------------|
| `buildNumber`   | string  | yes  | The build number as shown in TeamCity.                   |
| `agentName`     | string  | no   | Name of the build agent that ran the build.              |
| `agentHostName` | string  | no   | Host name of that agent.                                 |
| `agentVersion`  | string  | no   | TeamCity agent version of that agent.                    |
| `agentOs`       | string  | no   | Operating system reported by that agent.                 |
| `agentIsCloud`  | boolean | no   | Present and `true` when TeamCity identifies the build agent as a cloud agent. |
| `trigger`       | object  | no   | What initiated the run (see below). Absent when no origin can be determined. |

The TeamCity server version is not repeated here; it appears once as `runDetails.builder.version.teamcity`.

### `trigger` object

What initiated the build, as recorded by the platform. Always carries `type`; the remaining fields
appear only when applicable.

| Field      | Type   | Req. | Meaning                                                                                                                                                                                                        |
|------------|--------|------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `type`     | string | yes  | `user` for a user-initiated build; `snapshotDependency` when triggered as part of a snapshot-dependency chain; otherwise the trigger type id of an automated trigger (e.g. `vcsTrigger`, `schedulingTrigger`). |
| `username` | string | no   | The triggering user's username. Present for `user` triggers that have one.                                                                                                                                     |
| `userId`   | number | no   | The triggering user's numeric id. Present for `user` triggers.                                                                                                                                                 |

## `buildDefinition.resolvedDependencies`

The inputs that influenced the build. Two kinds of entry appear, each an in-toto
`ResourceDescriptor`.

### VCS sources

One entry per build revision (the exact commit the build was based on):

| Field                    | Type   | Req. | Meaning                                                                  |
|--------------------------|--------|------|--------------------------------------------------------------------------|
| `uri`                    | string | yes  | Repository URL. Git roots are prefixed `git+` (e.g. `git+https://….git`).|
| `digest.gitCommit`       | string | yes  | The resolved commit revision.                                            |
| `name`                   | string | yes  | VCS root name.                                                           |
| `annotations.branch`     | string | no   | Repository branch recorded for the revision.                            |
| `annotations.author`     | string | no   | Commit author, when the commit is known to the server.                  |
| `annotations.message`    | string | no   | First line of the commit message, limited to 200 characters.              |
| `annotations.committedAt`| string | no   | Commit timestamp (RFC 3339).                                            |

`digest.gitCommit` always comes from the build revision recorded by the server; the `author`,
`message`, and `committedAt` annotations are best-effort enrichment and may be absent (e.g. if the
VCS root was deleted after the build).

### Upstream builds

One entry per **direct** snapshot/artifact dependency whose build actually ran (deduplicated; entries
whose dependency never produced a build are omitted):

| Field  | Type   | Req. | Meaning                                                                 |
|--------|--------|------|-------------------------------------------------------------------------|
| `uri`  | string | yes  | Results-page URL of the upstream build. |
| `name` | string | yes  | `<buildTypeExternalId> #<buildNumber>` of the upstream build.           |

These entries carry no `digest`. The URL identifies the upstream build; provenance is available there
only if that build generated it.

## `runDetails`

### `runDetails.builder`

| Field                          | Type   | Meaning                                                                                       |
|--------------------------------|--------|-----------------------------------------------------------------------------------------------|
| `id`                           | string | Platform identity: the configured TeamCity server URL (project-aware). It is the verifier's trust anchor. |
| `version.teamcity`             | string | Full TeamCity server version.                                                                  |
| `version.teamcity-slsa-plugin` | string | Version of this plugin — the server-side component that generated and signed the provenance. Omitted if unknown. |

Per SLSA, `builder.id` ideally resolves to documentation of the platform's scope, claimed level, and
any unverified tenant-controlled fields; here that role is served by this build type document
together with the plugin's integration guide.

### `runDetails.metadata`

| Field          | Type   | Meaning                                                                       |
|----------------|--------|-------------------------------------------------------------------------------|
| `invocationId` | string | Results-page URL of this specific build run (`<server>/buildConfiguration/<buildTypeId>/<buildId>`), distinct from `builder.id`. |
| `startedOn`    | string | Build start time (RFC 3339).                                                  |
| `finishedOn`   | string | Build finish time (RFC 3339).                                                 |

## Secret handling

Build parameters are omitted by default. Enabling `slsa.includeCustomBuildParameters` includes
requester-supplied custom parameters after filtering declared secrets as described above.
Configuration defaults are not included. Plain parameter values are published unchanged;
do not put secrets in them. Provenance is not confidential.

## Completeness and limitations

- Subjects cover file artifacts visible server-side in the default view. Artifacts stored in external
  storage are included as long as the server can enumerate and read them.
- `resolvedDependencies` covers VCS revisions and **direct** build dependencies. Transitive build
  dependencies are not expanded. Consult upstream provenance where available.
- `runDetails.builder.id` and `metadata.invocationId` are derived from the configured server URL; if
  that setting is incorrect, these values will be incorrect (see the integration guide).
- For *personal* builds, the resolved source is under-specified: a personal build applies an
  uncommitted patch on top of the VCS revision, and that patch is not represented in
  `resolvedDependencies`. The `externalParameters.personal` flag is the signal that this occurred.
- Upstream build dependencies are recorded with a URL and name, without artifact digests.
- `externalParameters` omits build parameters by default; the `slsa.includeCustomBuildParameters` option
  publishes the requester-supplied custom parameters with declared secrets redacted (best-effort —
  declared secrets only). Configuration defaults are not included.

## Example

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    { "name": "dist/app.jar", "digest": { "sha256": "9f86d0818..." } }
  ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://iaroslav-molochkov.github.io/teamcity-slsa-plugin/buildtype/v1",
      "externalParameters": {
        "buildTypeId": "MyProj_Build",
        "projectId": "MyProj",
        "branch": "master"
      },
      "internalParameters": {
        "buildNumber": "1.0.1",
        "agentName": "agent-1",
        "agentHostName": "agent-1.ci.internal",
        "agentVersion": "2026.1 (build 999)",
        "agentOs": "Linux, version 6.1.0",
        "agentIsCloud": true,
        "trigger": { "type": "user", "username": "jdoe", "userId": 99 }
      },
      "resolvedDependencies": [
        {
          "uri": "git+https://github.com/acme/app.git",
          "digest": { "gitCommit": "abc123def456" },
          "name": "app-repo",
          "annotations": {
            "author": "John Doe",
            "branch": "refs/heads/master",
            "committedAt": "2026-06-23T09:58:00Z",
            "message": "Fix the bug"
          }
        },
        {
          "uri": "https://teamcity.example.com/buildConfiguration/Lib_Build/7",
          "name": "Lib_Build #3.2"
        }
      ]
    },
    "runDetails": {
      "builder": {
        "id": "https://teamcity.example.com",
        "version": {
          "teamcity": "2026.1 (build 999)",
          "teamcity-slsa-plugin": "1.0.0"
        }
      },
      "metadata": {
        "invocationId": "https://teamcity.example.com/buildConfiguration/MyProj_Build/42",
        "startedOn": "2026-06-23T10:00:01Z",
        "finishedOn": "2026-06-23T10:05:00Z"
      }
    }
  }
}
```

## Versioning

This is `v1`. Once released, additive, backward-compatible changes (new optional fields) may be made
within `v1`. Any change to the meaning or shape of an existing field, or a removal, requires a new
build type URI (`…/buildtype/v2`); the `v1` URI then remains stable for already-issued attestations.
